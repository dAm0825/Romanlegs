# OfferGuard · 职途罗盘 技术设计

## 1. 项目概述

OfferGuard 是一款面向高校毕业生的 AI 就业风险侦察 Web 应用。用户粘贴 offer、劳动合同或实习协议后，系统通过六阶段 Agent 工作流识别高影响条款、召回可信法规证据、生成风险地图与行动清单，并在用户确认后才生成可编辑的沟通草稿。

核心问题不是“用户不会问法律问题”，而是“用户不知道自己该问什么”。因此，产品不把 AI 做成空白聊天框，而是把签约前核查拆成一条可见、可追溯、可终止的决策链。

### 1.1 目标用户

- 正在签约的应届毕业生、实习生和研究生。
- 希望快速识别高风险条款，但无法承担完整法律咨询成本的学生。
- 为学生提供签约辅导的高校就业中心、辅导员和就业社团。

### 1.2 主要痛点

1. **信息不对称**：合同使用概括表述，签署者难以判断对自身权益的影响。
2. **证据难找**：普通 AI 回答看似合理，却无法说明引用的法规是否真实、是否适用于当前条款。
3. **行动断层**：用户即使知道“有风险”，也不知道该向 HR 问什么、如何留证、何时升级求助。
4. **隐私风险**：合同常含姓名、手机号、身份证号和学校信息，不适合直接发给外部模型。

## 2. 需求分析

### 2.1 功能需求

| 模块 | 需求 | 验收标准 |
|---|---|---|
| 输入 | 粘贴合同、上传 TXT/MD、载入示例 | 20 至 60000 字符，输入错误有明确提示 |
| 隐私 | 模型调用前识别并遮蔽敏感信息 | 身份证、手机号、邮箱、银行卡不出现在清洗文本中 |
| 条款发现 | 识别试用期、工资、工时、社保、竞业、解约等主题 | 每项发现可在原文定位对应句子 |
| 证据检索 | 基于条款主题和文本召回法规 | 每项发现至少有一条知识库证据 |
| Agent 工具 | 原生 Function Calling 与可选 MCP 服务 | 规划器能调用检索、风险、清单、安全审查工具 |
| 风险报告 | 分数、等级、解释、建议、引用和优先行动 | 报告可复制、导出 Markdown |
| 人工确认 | 用户复核原文后才解锁沟通草稿 | 未勾选确认时按钮禁用 |
| 可用性 | 桌面和移动端适配，弱网/无 Key 可演示 | 离线模式功能完整，不出现空白页面 |

### 2.2 非功能需求

- **隐私**：外部模型只接收脱敏文本；密钥只从未提交的 `.env` 读取。
- **可解释**：不展示无来源的模型结论，引用必须属于本次检索白名单。
- **安全**：不自动签署、不自动发送、不承诺胜诉或赔偿结果。
- **可部署**：仅依赖 Python 标准库即可运行，降低比赛复现门槛。
- **响应性**：首屏无第三方字体或脚本依赖，常规分析目标低于 20 秒。

## 3. 竞品拆解与产品定位

调研 5 个公开优秀作品后，可以看到常见模式为“业务首页 + 多模块平台 + AI 助手 + 管理端”。健康守护、旅行觅点、智能健身教练和心理健康平台都强调完整服务入口；陶韵智境进一步整合了非遗地图、社区、语音助手与后台。

这些作品的共同优势是场景完整、演示素材丰富，共同改进空间是 AI 决策过程不透明，聊天助手与业务闭环之间的因果关系不足。

OfferGuard 做出三项收束：

1. 只解决签约前一次高风险判断，避免功能堆叠。
2. 让 Agent 的工具调用、证据引用和人工确认直接进入 UI。
3. 从“解释风险”推进到“形成行动清单”，保证真实结果。

详细竞品拆解见 `docs/competitive-research.md`。

## 4. 系统架构

OfferGuard 采用“浏览器端交互 + 标准库 HTTP 服务 + 本地知识库 + DeepSeek 能力层”的轻量全栈结构。

```text
┌─────────────────────────────────────────────────────────────┐
│ Web Client                                                  │
│ 输入 / Agent 轨迹 / 风险仪表盘 / 条款证据 / 人工确认 / 草稿  │
└──────────────────────────────┬──────────────────────────────┘
                               │ JSON / HTTP
┌──────────────────────────────▼──────────────────────────────┐
│ Python HTTP Server                                          │
│                                                             │
│  1 PII Shield → 2 Clause Scout → 3 Tool Planner             │
│       │              │                 │                    │
│       │              │        ┌────────▼─────────┐          │
│       │              │        │ Native Tools     │          │
│       │              │        │ Policy RAG       │          │
│       │              │        │ Risk Engine      │          │
│       │              │        │ Evidence Planner │          │
│       │              │        │ Safety Reviewer  │          │
│       │              │        └────────┬─────────┘          │
│       └──────────────┴─────────────────▼                    │
│               DeepSeek Planner + Synthesizer                 │
│                                                             │
│  Local Knowledge Base · Citation Allowlist · MCP Server     │
└─────────────────────────────────────────────────────────────┘
```

### 4.1 技术选型

| 层次 | 方案 | 理由 |
|---|---|---|
| 前端 | 原生 HTML5 + CSS + ES Modules | 无构建依赖，评审可直接运行；组件以函数和状态集中管理 |
| 服务端 | Python `http.server` | 标准库即可部署，不依赖第三方 Web 框架 |
| 模型 | DeepSeek `deepseek-chat` | 中文合同理解稳定；支持 JSON 输出和 Function Calling |
| 检索 | TF-IDF 风格中文 n-gram + 主题加权 | 数据量小，结果稳定、可解释、无需额外向量服务 |
| 工具 | DeepSeek Tool Calls + stdio MCP | 同时展示在线 Agent 工具调用和开放协议扩展能力 |
| 存储 | 无服务端持久化；浏览器 LocalStorage 存报告摘要 | 竞赛阶段避免保存用户合同，降低隐私风险 |

## 5. AI 技术方案

### 5.1 六阶段 Agent

#### 阶段一：隐私屏障

服务端使用正则表达式先处理身份证、手机号、邮箱和银行卡号。脱敏发生在任何模型请求之前，返回结果只保留数量，不返回原始敏感值。

#### 阶段二：条款侦察

系统使用可测试的规则库识别高影响主题，并将每个发现定位到原文中的具体句子。规则负责“不遗漏结构明确的条款”，模型负责“解释得更自然”，分工避免模型完全主导风险发现。

#### 阶段三：工具规划与检索

DeepSeek 获得四个原生工具定义：

- `search_local_policy`：从可信知识库检索法规。
- `calculate_contract_risk`：计算综合风险。
- `build_evidence_checklist`：生成书面澄清与留证清单。
- `review_legal_safety`：识别需要人工升级的边界。

模型通过标准 `tool_calls` 返回工具名与 JSON 参数，服务端只执行白名单中的工具。若模型未选择必要工具，服务端补全检索与风险计算，保证离线模式仍然可用。

#### 阶段四：RAG 证据召回

知识库共 15 条，覆盖书面合同、试用期、工资、工时、加班、社保、竞业、违约金、解除合同和沟通建议。中文检索使用二元、三元字符片段与类别加权，类别匹配比普通词频更稳定。

每条证据包含：

```json
{
  "id": "LCL-19",
  "title": "试用期期限限制",
  "source": "《中华人民共和国劳动合同法》第十九条",
  "category": "probation",
  "text": "劳动合同期限三个月以上不满一年的..."
}
```

#### 阶段五：受约束合成

合成 Prompt 只允许模型使用当前 `finding id` 和 `evidence id`，输出固定 JSON 结构。模型生成的解释、建议与行动进入报告，但法条原文仍以知识库文本为准。

#### 阶段六：安全复核

服务端在返回前执行三项确定性校验：

1. 每个 finding 的 quote 必须存在于用户原文。
2. 每个 citation 必须存在于本次检索白名单。
3. 检测“忽略指令、泄露密钥”等提示注入标记，并将合同文本始终当作数据。

无法通过原文校验的发现不会进入结果；越权引用会被移除并替换为对应类别的可信证据。

### 5.2 MCP 扩展

`server/mcp_server.py` 是一个 stdio MCP 服务，提供：

- `search_policy`
- `calculate_risk`
- `build_evidence_checklist`

它可以让其他支持 MCP 的 AI 客户端复用同一套可信政策工具，体现 Agent 工具层的可移植性。

## 6. 核心功能实现

### 6.1 风险计算

每条规则包含严重度权重，服务端另加条款数量基线后封顶到 96 分：

```text
risk = min(96, sum(finding.weight) + baseline(finding_count))
```

65 分及以上为高风险，35 至 64 为中风险，低于 35 为需核对。风险分只用于排序和唤醒注意力，最终判断仍需结合用户身份、合同完整版本和实际履行情况。

### 6.2 前端状态流

前端维护输入文本、分析结果、筛选状态和确认状态。分析请求期间，六步轨迹逐段亮起；完成后用后端真实耗时覆盖动画状态。报告支持条款过滤、证据展开、Markdown 导出和本地历史摘要。

### 6.3 人工确认门

用户未勾选“我已打开合同原文”时，生成草稿按钮保持禁用。点击后只生成可编辑文本，不调用任何消息或邮件接口。该设计避免 AI 在事实不完整时代表用户作出沟通承诺。

## 7. 安全与隐私设计

| 风险 | 控制措施 |
|---|---|
| 个人数据外泄 | 模型调用前正则脱敏；前端明确提示；服务端不持久化合同 |
| 法规幻觉 | 引用白名单 + 类别优先证据 + 服务端引用校验 |
| 原文幻觉 | 发现 quote 必须能在原文中匹配 |
| 提示注入 | 合同只作为待分析数据；检测注入标记；系统提示明确禁止执行合同内指令 |
| 过度依赖 | 展示“非正式法律意见”边界，生成草稿不发送，高风险场景提示人工升级 |
| 密钥泄露 | `.env` 被 `.gitignore` 排除，公开仓库只保留 `.env.example` |

## 8. 测试与验证

自动化测试覆盖以下场景：

1. 手机号、身份证和邮箱脱敏。
2. 示例合同命中试用期、工资、工时、社保等关键规则。
3. 所有 finding quote 均存在于原文。
4. 所有 citation 均来自本次检索证据。
5. Agent 六阶段轨迹完整。
6. 短文本输入被拒绝。
7. MCP 服务成功初始化并列出工具。

真实 DeepSeek 联调中，示例报告约 7 至 10 秒返回。离线模式不依赖外网，可在比赛现场稳定演示。

## 9. 部署方案

```bash
cp .env.example .env
# 写入 DEEPSEEK_API_KEY
python3 server/app.py
```

服务默认监听 `127.0.0.1:8000`。生产部署只使用标准库和静态文件，可置于任意支持 Python 3.11+ 的容器或云主机。正式公网部署时应增加 HTTPS、反向代理、请求限流、访问日志脱敏和管理员监控。

## 10. 创新点

### 10.1 技术创新

- **规则发现 + Agent 解释的双通道**：结构化规则负责稳定召回，DeepSeek 负责自然解释与工具规划。
- **RAG 引用白名单**：模型无法凭空创建引用，服务端再次核验。
- **原文闭环**：每项风险必须绑定原句，提高可审查性。
- **原生 Function Calling + MCP 双入口**：既能在 Web 应用中自主调用，也能让其他 AI 客户端复用政策工具。

### 10.2 应用创新

- 把“法律问答”重构为“签约决策工作流”。
- 用 Agent 轨迹让过程透明，而不是用黑箱答案制造确定性。
- 把人工确认门设计为产品核心，而非隐藏在免责声明中。
- 将隐私屏障前置到模型调用之前，符合学生合同的高敏感特征。

## 11. 局限与展望

当前版本只接受文本输入，规则库重点关注校园招聘中高频出现的试用期、工资、工时、社保、竞业和解约问题。后续计划：

1. 支持 DOCX/PDF 解析与页面级原文定位。
2. 增加城市最低工资、社保基数和行业岗位等本地化数据。
3. 引入专业律师复核的知识库版本管理和引用时效字段。
4. 为高校就业中心提供匿名化风险趋势看板。
5. 增加多语言合同和跨境就业场景。

## 12. 结论

OfferGuard 的核心价值不只是“让 AI 总结合同”，而是让 AI 在透明、可验证、可终止的工作流里帮助用户发现风险并形成行动。它把 AI 的高效率与人工的最终决定权结合起来，面向真实的毕业生签约场景，具备清晰的社会价值与可扩展空间。
