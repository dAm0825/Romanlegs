# 优秀作品拆解与 OfferGuard 的差异化定位

## 调研样本

调研了用户提供的 5 支第八届“传智杯”AI Web 开发挑战赛演示视频。公开标题、简介和演示画面显示：

| 作品 | 核心场景 | 主要结构 | 可借鉴处 | 容易同质化的地方 |
|---|---|---|---|---|
| 健康守护 | 健康咨询、饮食规划、运动推荐、心理陪伴 | 首页 → 专科服务卡 → 问卷/对话 → 建议 | 服务入口清晰，功能覆盖完整 | 多个模块并列，AI 容易成为附属聊天入口 |
| 旅行觅点 | 旅游信息筛选、收藏推荐、评论互动 | 信息流 → 多维筛选 → 详情 → 互动 | 真实痛点明确，业务闭环完整 | 偏信息平台，AI 价值与普通推荐算法边界不够明显 |
| 智能健身教练 | 健身计划、动作训练、进度反馈 | 首页 → 训练方案 → 陪练 → 数据统计 | 视觉主题统一，行动目标明确 | 同类数字健康产品较多，难形成独特交互 |

| 陶韵智境 | 非遗展示、论坛、知识地图、语音 AI 助手 | 文化展示 + 社区 + 地图 + AI 助手 + 后台 | 内容组织丰富，AI 助手接入 DeepSeek，文化叙事鲜明 | 功能栈较多，AI Agent 与业务决策链的关系仍可更深 |

## 共性特征

这些作品通常具备三个层次：

1. **场景层**：从健康、旅行、健身、心理和非遗等真实生活议题切入。
2. **产品层**：使用“首页 + 核心功能 + 用户中心/管理端”的平台结构。
3. **展示层**：在 5–8 分钟内依次展示首页、核心流程、AI 亮点、技术方案和成果。

共同不足也很清晰：多数 AI 能力以“对话助手”呈现，用户只看得到最终回答，看不到 Agent 如何规划、调用了什么工具、依据是什么，以及哪些结论必须由人确认。

## OfferGuard 的差异化

### 1. 从“功能集合”收束到一条高风险决策链

OfferGuard 不做泛化的就业咨询平台，只解决毕业生签约前最容易吃亏的一步：**看懂 offer 和合同中真正影响自己的条款**。主流程只有一个，但每一步都有可见结果。

### 2. 把 AI 过程变成产品界面

界面持续展示 Agent 的六个阶段：隐私屏障、条款侦察、证据检索、风险计算、行动规划、安全复核。用户可以展开每一次工具调用，看到检索了哪些法规、为什么给出该风险等级。

### 3. 证据优先，拒绝“模型说了算”

风险结论必须绑定知识库证据；前端明确区分法规原文、产品解释和建议行动。模型不能生成数据库中不存在的引用编号，服务端还会复核引用是否真实存在。

### 4. Human-in-the-loop 是核心交互

系统不会自动替用户回复 HR。它先形成可核对的行动清单，用户勾选“已核对原文”后才能生成沟通草稿，从而把 AI 定位为决策辅助者而非替代者。

### 5. 隐私保护发生在模型调用之前

合同往往包含姓名、电话、学校、身份证等敏感信息。服务端先在本地脱敏，再把清洗后的文本发送给 DeepSeek；脱敏数量会直接显示在 Agent 轨迹中。

## 评审维度映射

| 官方维度 | OfferGuard 对应设计 |
|---|---|
| AI 技术深度 | 规划与合成两阶段 Agent、可解释 RAG、规则引擎、引用校验、DeepSeek API |
| 创新性 | 面向签约决策的“Agent 证据链 + 人工决策门”，而非通用聊天框 |
| 前端工程质量 | 原生 ES Modules、组件化渲染、无第三方运行时依赖、可访问性和响应式布局 |
| 实用性 | 直接缩短毕业生核查合同的时间，输出可执行行动清单与沟通草稿 |
| 用户体验 | 单页低认知负担流程、实时阶段反馈、风险仪表盘、证据可展开 |
| 社会价值与商业潜力 | 降低初入职场者的信息不对称，可扩展至高校就业中心与公益法律援助 |
